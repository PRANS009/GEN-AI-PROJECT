# Security design and release tests

| Boundary | Design | Evidence required before release |
| --- | --- | --- |
| Identity and tenancy | Verify Supabase tokens server-side. Use PKCE and allowlisted callback URLs. Apply same-origin checks and CSRF protection to cookie-authenticated mutations. Verify ownership inside every service and child-resource lookup. | New user registration and sign-out, expired session, rejected cross-origin mutation, two actual accounts and two keys with overlapping resource names. |
| Developer credentials | Use 32 cryptographically random secret bytes and a separate public selector. Display the bearer once over TLS on creation/rotation with no-store headers. Store a SHA-256 digest of the high-entropy secret, compare fixed-length digests in constant time, and reject revoked keys. Restrict management to user sessions. | Wrong secret, missing scope, atomic rotation, old key rejected immediately, other owner's keys inaccessible, no secret in listings or telemetry. |
| Quotas | Reserve usage atomically in PostgreSQL before provider or sandbox work. Start with 30 API requests/min/key, 60/min/owner, 5 AI requests/min/owner and a configurable project-wide AI daily allowance derived from live provider quota. Use expiring concurrency leases. | Concurrent requests on two function instances obey shared budgets. Return 429 and Retry-After. Revoking one key leaves other keys functional. |
| SQL sandbox | Disposable WASM SQLite instance in a worker with an in-memory VFS, no extension loading, file-backed databases, network or host callbacks accessible from SQL. Engine authorizer restricts operations, PRAGMAs, functions and attachment. Enable defensive mode, lower SQLite limits and disable trusted schema. Separate grading policy permits reads only. | Prove isolation, safe writes, rollback, timeout and memory ceilings on a preview cold start. A worker thread alone is insufficient isolation. If the package cannot enforce the WASM memory ceiling, build the restricted SQLite module with an explicit maximum before exposing execution. |
| Resource exhaustion | Initial design budgets: 16 KiB SQL, 2 seconds of engine execution, 64 MiB maximum linear memory, 1 MiB snapshot, 200 displayed rows and 256 KiB serialized response. Cap individual values, SQL complexity and temporary pages. Use progress interruption plus an independent watchdog and cleanup. Pagination or an explicit truncation flag is mandatory. | Exercise limits independently, including a small row count with large values. On failure discard the working copy, record one failed execution and retain the last committed state. |
| Model boundary | Use only server-resolved schema/context. Scope threads by owner/dataset. Use the supplied dedicated system prompt, bounded input/output, strict JSON validation and schema preparation. Render provider output as text. Prevent automatic execution and mark potentially destructive SQL using engine classification. | Clarifying question, invalid model JSON, unknown column, generated write, empty/safety-blocked response, timeout, quota exhaustion and cross-owner thread tests. |
| Outbound webhooks | Require HTTPS on port 443, reject credentials and nonpublic destinations. Resolve all A/AAAA records on registration and every attempt. Deny mixed, special-use, private, link-local and IPv4-mapped private addresses. Pin the connection to a checked public IP, retain original hostname for TLS/SNI verification, verify peer address and disable redirects/proxies. Limit endpoints, payload size, concurrent sends and response bytes. | Unit-test address classification and DNS changes with controlled doubles. Integration-test public delivery, redirect rejection, timeout, invalid TLS and bounded retries. |
| Replay and delivery | Encrypt recoverable per-endpoint signing secrets with authenticated encryption and a versioned server key. Sign timestamp, period and exact raw JSON bytes using HMAC-SHA256. Document constant-time verification, five-minute timestamp tolerance and event-ID deduplication. | Verify valid/tampered/stale payloads, duplicate deliveries, crash recovery and receiver success after a transient failure. |
| Browser and exports | Escape SQL, messages, schema names and cells. Use a restrictive CSP compatible with local editor workers, secure cookies and no-store for private results. Neutralize spreadsheet-formula prefixes in text cells when exporting CSV. Preserve typed values in JSON. | Verify unsafe-looking text renders literally and exported text cannot become an executable spreadsheet formula. |
| Application database and logs | Use typed parameterized operations, least privilege, RLS and restricted function grants. Keep student SQL entirely outside application SQL construction. Log IDs, status, route, timings and error class. Redact headers, raw SQL, prompts, callback query strings and provider error bodies in infrastructure logs. | Migrate a clean DB, verify grants and owner policies as two users, exercise role-restricted RPCs, review generated client bundle and staged files for secrets. |

## Webhook delivery policy

Return success on a 2xx response. Retry transport timeouts, 408, 429 and 5xx failures. End an attempt on a redirect or unverifiable destination. Recheck endpoint enablement and owner before sending. Use a three-second request deadline, bounded batch size and expiring delivery leases. Start with five total automatic attempts, after approximately 1, 5, 15 and 60 minutes plus bounded jitter. Honor Retry-After within the configured window. After exhaustion expose the failed state; allow a rate-limited manual retry on the same event ID and preserve prior attempts. A receiver can see the same event more than once.

## Secret handling and operations

Keep local environment files out of Git. Supply public Supabase URL and publishable key only to the browser. Keep Gemini, privileged database access, webhook encryption and dispatch secrets server-only. Store the scheduler invocation credential in Supabase Vault. Use independent values and databases for preview and production. Rotate API and signing keys without printing or storing plaintext in logs. Time-limit raw query history, expired practice sessions and delivery-attempt retention. The Phase 6 runbook will specify cleanup, key replacement and verified recovery steps.
